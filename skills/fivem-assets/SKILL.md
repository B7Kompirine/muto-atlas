# FiveM Asset Verisi — önce bak, sonra kod yaz

## TEMEL KURAL

**Bir obje/prop/kapı/animasyon hakkında kod yazmadan önce o asset'in verisine
bakılır.** Native denemek, "şunu da ekleyelim" demek, üç farklı yaklaşımı
sırayla denemek — bunlar veriye bakmamanın maliyetidir.

Somut örnek (gerçek vaka): Fleeca vezne kapısı `v_ilev_gb_teldr` bir türlü
açılmadı. `AddDoorToSystem`, `FreezeEntityPosition`, `SetEntityDynamic`,
`NetworkRequestControlOfEntity` sırayla denendi. Cevap ytyp'nin tek satırındaydı:

```
specialAttribute = 0   → bu obje kapı DEĞİL, kapı sisteminde menteşesi yok
```

Tek sorgu (`assetdb.py door v_ilev_gb_teldr`) bunu baştan söylerdi.

## OTOMATİK SORGU TABLOSU — kullanıcı komut vermez, sen bakarsın

Bu skill bir **kütüphanedir**: aşağıdaki konu geçtiği anda, kullanıcı hiçbir
komut yazmasa bile ilgili sorgu **kod yazmadan önce** çalıştırılır. Sonucu
kullanıcıya özetle, sonra koda geç.

| Konu geçtiğinde | ÖNCE bunu çalıştır |
|---|---|

geldiğini söyle. Bit tabloları `references/ytyp-ymap-bayraklari.md`'de.

**Sessiz hata sınıfı — bu konularda uyarmadan geçme:**
- yanlış yazılmış `fxName` → efekt hiç çıkmaz, hata da vermez
- animasyon ytyp'inde BB min/max kutusu yok → obje uzakta titrer ve kaybolur
- bake edilmemiş animasyon → oyunda ölçeklenir (CodeWalker'da doğru görünür)
- LOD zincirinden bir halka eksik → tüm zincir bozulur
- mesh collision + `Dynamic` → obje yerin içine düşer
- `.ycd` her zaman XML çıkar (`target_formats` ona ulaşmaz) → `xml_to_ycd.ps1`

## OYUNA GİRMEDEN DOĞRULA — CodeWalker merdiveni

**Tam reçete: `references/oyuna-girmeden-dogrulama.md`**
Araç: `scripts/cw_anim_check.ps1`

Bir asset'i (animasyon, doku, model, ytyp) test etmek için sunucuya
bağlanmak **en son çaredir**. FiveM stream dosyalarını cache'lediği için
her oyun-içi tur tam çıkış + yeniden bağlanma gerektiriyor. Sistemde
CodeWalker varsa (`CodeWalker.Core.dll`) doğrulamanın büyük kısmı
saniyeler içinde, oyun açılmadan yapılır.

**Kural: bir basamakta yakalanabilecek hatayı alt basamağa taşıma.**

| Ne doğrulanacak | Basamak |
|---|---|
| ağırlık, deform, pivot, ölçü | Blender'da **ölç** (`evaluated_get`) |
| shader/bucket, kemik tag, hiyerarşi, `<Hash>`, klip sayısı | `res_to_xml.ps1` + vanilla ile **yapısal diff** |
| klip eğrisi, faz→değer, genlik, ölü kuyruk | `cw_anim_check.ps1` (headless CodeWalker.Core) |
| "gözle doğru duruyor mu" | Blender render → **kullanıcıya dosya gönder** |
| vanilla asset incelemek, dünya yerleşimi, MLO düzeni | CodeWalker GUI (**elle**, kullanıcı sürer) |
| script, fizik, gerçek görünüm, streaming, resmon | **oyun** |

- `CodeWalker.Core.dll` bir kütüphanedir: Model Viewer'ın animasyon
  değerlendirme kodu (`GetFramePosition` + `EvaluateVector4/Quaternion`)
  headless çağrılabilir. Klibin hangi kemiğe hangi fazda ne yazdığı
  **sayıyla** okunur.
- **Headless denetim görsel onayın yerine geçmez.** Sayı "doğru" dese de
  kullanıcı göremez; render alıp **dosya olarak ilet**, klasör yolu verme.
- `ClipBase.Name` OKUMA → StackOverflow, süreç exit 253, hata mesajı yok.
- `Add-Type`'a **`netstandard`** referansı şart; `Animation.BoneIds` dizi
  değil → `.data_items`.
- CodeWalker GUI'de `LoadClipDict(string)` sözlüğü **ada göre oyun
  verisinden** çözer: resource klasöründeki serbest `.ycd` listede çıkmaz.
- CodeWalker taşınabilir `.exe` ise computer-use `request_access` onu
  bulamaz → GUI basamağını ajan **süremez**, kullanıcıya tarif verir.
- **Ardışık kliplerde birleşme noktasını ölç.** Klipler mutlak kemik
  dönüşümü yazar: A'nın son karesi ile B'nin ilk karesi **her kanalda**
  eşleşmezse tek karede sıçrar. İki kez yaşandı — biri seviye (dolum %100,
  çalkalanma %72 → sıvı zıpladı), biri eğim (dolum 0.00°, çalkalanma 9.00°
  → "frame skip" görüntüsü). Her klip nötr başlar, nötr biter; ortak
  seviye **tek sabitten** gelir (üretici + önizleme + Lua aynı sabiti okur).
- **Hareketin fiziği de ortak sabit olmalı** — frekans, tepe genliği,
  sönüm. Konum/açı tutsa bile farklı sabitler *hız değişimi* gibi görünür:
  **algılanan hız genliğe bağlıdır**. Yaşandı: sönüm 2.6 vs 2.0, genlik
  5.5° vs 9.0° → "dalgalanma sönerken bir anda darbe alıp hızlanıyor".
  Denetim: iki klibi sönüm başlangıcına hizalayıp aynı sürelerde ölç.
- **Önizleme render'ı klip formülleriyle aynı modülden beslenmeli**, yoksa
  kullanıcıya asset'te olmayan bir davranış gösterilir.

### Çıkış kodları — bir kapıya bağlıyorsan bunlara bak

`assetdb.py` dört ayrı kod döndürür. **Hepsini `!= 0` diye okumak yanlıştır:**

| kod | anlam | ne yapmalı |
|---|---|---|
| 0 | bulundu | devam |
| 1 | sorgu çalıştı, **ad otoritede yok** | asset gerçekten yok ya da yanlış yazılmış |
| 2 | **veri katmanı kurulu değil** | sonuç hakkında HİÇBİR ŞEY denemez — build betiğini çalıştır |
| 3 | iç hata (bozuk dosya, istisna) | veri bozuk, "yok" DEĞİL |

`2` ile `1`'i karıştırmak, katman eksik olduğu için çıkan "0 sonuç"u
"bu asset oyunda yok" diye okumaktır — ev kuralı: *aracın göstermemesi,
o şeyin yok olduğu anlamına gelmez.*

```bash

# Animasyon
python "${CLAUDE_PLUGIN_ROOT}/scripts/assetdb.py" anim <terim>
python "${CLAUDE_PLUGIN_ROOT}/scripts/assetdb.py" anim <dict> --dict
python "${CLAUDE_PLUGIN_ROOT}/scripts/assetdb.py" scenario <terim>

# İndeks durumu
python "${CLAUDE_PLUGIN_ROOT}/scripts/assetdb.py" stats

# Modelin ekranı var mı — shader/doku eşlemesi (AddReplaceTexture için)
powershell -NoProfile -ExecutionPolicy Bypass \
  -File "${CLAUDE_PLUGIN_ROOT}/scripts/screentex.ps1" -Model <model adı> -All
```

İndeks vanilla RPF'lerden (CodeWalker.Core ile) + sunucunun kendi ytyp'lerinden
üretilir. Yeniden kurmak için `/asset-build`.

## specialAttribute — KAPI TABLOSU

316k archetype'ın dağılımından doğrulandı, tahmin değil:

| Değer | Anlam | Kapı sistemi çalışır mı |
|---|---|---|
| **7** | menteşeli kapı | ✅ evet — `AddDoorToSystem` + `DoorSystemSetDoorState` |
| **8** | sürgülü kapı | ✅ evet |
| **5** | garaj / rulo kapı | ✅ evet |
| **10** | kepenk / asansör kapısı | ✅ evet |
| **12** | demiryolu bariyeri | ✅ evet |
| **0** | kapı DEĞİL | ❌ hayır — kayıt olsa bile obje kımıldamaz |
| diğer | bitki, mobilya, trafik, SLOD... | ❌ hayır |

`specialAttribute = 0` ise:
1. Kapı sistemi **hiçbir şey yapmaz** — denemeye değmez.
2. Tek script-içi yol: `SetEntityHeading` ile transform'u yeniden yazmak.
   Doğru görünmesi için pivot'un kenarda olması gerekir → `show` çıktısındaki
   bbox yorumu bunu söyler.
3. Kalıcı doğru çözüm: ytyp override ile `specialAttribute = 7` vermek.

## OBJE HAREKET ETTİRMENİN KATMANLARI

Bir dünya objesini oynatmak isterken sırayla doğrula:

1. **Sahiplik** — `SetEntityAsMissionEntity` + `NetworkRequestControlOfEntity`.
   Kontrol alınmadan `FreezeEntityPosition` / `SetEntityCoords` /
   `SetEntityHeading` **sessizce yok sayılır**. En sık atlanan adım budur.
2. **Fizik** — `FreezeEntityPosition(false)` tek başına yetmez; obje
   "hareketsiz" işaretliyse `SetEntityDynamic(true)` + `ActivatePhysics()` gerekir.
3. **Menteşe** — kapı sistemi ancak `specialAttribute` uygunsa devreye girer.
4. **Senkron** — harita objeleri networked DEĞİLDİR. Durum server'da tutulup
   her client kendi kopyasına uygular; yoksa sadece sende hareket eder.

## ANİMASYON — temel kurallar

- Animasyon **her zaman** dictionary + clip çiftidir. Biri eksikse oynamaz.
- Kalıp: `RequestAnimDict(dict)` → `HasAnimDictLoaded(dict)` bekle →
  `TaskPlayAnim(ped, dict, clip, ...)`.
- İndekste yoksa **o animasyon yoktur**. Benzer isim uydurma; kullanıcıya
  "bulamadım" de ve arama terimini değiştirerek tekrar dene.
- **Süreyi tahmin etme.** `.ycd`'den gelen gerçek süre indekste var:
  `anim <dict> --dict` çıktısındaki saniye değeri. Progress bar / `Wait()`
  süresini oradan al.

## PROP + KARAKTER BİRLİKTE (senkron sahne)

"Adam çantayı önüne alıp para dolduruyor" tipi sahneler tek bir ped
animasyonu değildir: **ped ve prop ayrı kliplerdir, senkron oynatılır.**

Doğru klip çiftini bulmak:

```bash
python "${CLAUDE_PLUGIN_ROOT}/scripts/assetdb.py" anim <dict> --dict
```

Çıktı klipleri **süreye göre gruplar**. Bir grupta *aynı süre ama farklı
kemik sayısı* varsa o bir ped+prop çiftidir — araç bunu işaretler:

```
[47.967s]  <-- ayni sure, FARKLI iskelet: ped + prop cifti
  bag_grab              47.967s  kemik=72    <- ped
  cart_cash_dissapear   47.967s  kemik=96    <- prop (para arabası)
```

Sadece "aynı süre" yetmez: `_female` / `_suit` / `_no_armour` varyantları da
aynı süredir ama hepsi ped'dir. Ayırt eden **kemik sayısının farklı olması**.

Oynatma zinciri (native imzaları doğrulandı):

```lua
local scene = NetworkCreateSynchronisedScene(x, y, z, rx, ry, rz, 2, true, false, 1.0, 0.0, 1.0)
NetworkAddPedToSynchronisedScene(ped, scene, dict, pedClip, 4.0, -8.0, 0, 0, 1000.0, 0)
NetworkAddEntityToSynchronisedScene(propObj, scene, dict, propClip, 4.0, -8.0, 0)
NetworkStartSynchronisedScene(scene)
```

Tek oyuncu / lokal sahne için `CreateSynchronizedScene` + `TaskSynchronizedScene`
+ `PlaySynchronizedEntityAnim(entity, scene, animation, propName, ...)`.

## FRAGMENT ÜRETİMİ (zincirin 1. adımı)

Bir prop'un çarpışması kemik animasyonuyla birlikte hareket etsin istiyorsan
tek yol **fragment**tir. Denenip elenen yollar:

- `ASSET_TYPE_DRAWABLE`: tek statik bound, entity transform'una bağlı.
  Kemik animasyonu sadece görseli oynatır, çarpışma yerinde kalır.
- **YED / expression**: ÇALIŞAN YOL BUDUR. Tam reçete:
  `references/yed-collision-animasyon.md`

  > ⚠️ Bu satırda önceden **"YED ile collision animasyonu diye bir şey yok"**
  > yazıyordu. YANLIŞTI ve saatlerce yanlış yöne gidilmesine sebep oldu.
  > Hatanın kaynağı: CodeWalker ile `.yed` açılıp `ExprMap.Count == 0`
  > görülmesi ve "dosya boş" sanılması. Gerçek şu ki **CodeWalker
  > expression bytecode'unu (Streams) YAZAMAZ, sadece okuyabilir** — ve bu
  > kullanımda `Streams` zaten boştur, iş `Tracks` tarafında döner.
  > Yani ölçülen şey aracın sınırıydı, dosyanın içeriği değil.
  > **Bir aracın bir şeyi göstermemesi, o şeyin yok olduğu anlamına gelmez.**

### Sollumz'da fragment kurma — bound'u kemiğe bağlayan şey

`parent_bone` **DEĞİL**, isim eşleşmesi de **DEĞİL**. Sollumz bağı
`COPY_TRANSFORMS` constraint'inden okur (`tools/blenderhelper.py`,
`get_child_of_bone`). Constraint yoksa `does_bone_have_collision` false
döner, kemik sessizce atlanır ve export **uyarı bile vermeden**
`PhysicsLODGroup`'u boş bırakır — dosya üretilir ama işe yaramaz.

Her collision objesi için:

```python
c = col_obj.constraints.new("COPY_TRANSFORMS")
c.target = frag_armature_obj
c.subtarget = "KemikAdi"
c.mix_mode = "BEFORE_FULL"   # set_child_of_constraint_space ile aynı
c.target_space = "POSE"
c.owner_space = "LOCAL"
```

Ayrıca:
- `bone.sollumz_use_physics = True` **sadece** collision'ı olan kemikte.
- `col_obj.child_properties.mass` varsayılan 0; 0 bırakılırsa archetype
  kütlesi de 0 olur. Bound hacmine göre dağıt.
- Kırılmasın istiyorsan `bone.group_properties.strength = -1`.
- Bound composite fragment armature'ının **doğrudan** çocuğu olmalı,
  drawable'ın altında değil.
- Kemik başına birden fazla bound serbesttir (`child_cols` kemik adına göre
  gruplanır).

### EN ÇOK VAKIT KAYBETTİREN TUZAK: kök grup

`parentIdx = 255` olan grup **entity gövdesidir**. Onun çarpışması entity
transformuna kaynaklıdır ve **kemiği takip etmez**. Tek gruplu bir fragment
üretirsen o grup zorunlu olarak kök olur; export kusursuz görünür,
`PhysicsLODGroup` dolu çıkar, ama oyunda animasyon oynar ve collision
yerinde kalır — yani hiçbir şey kazanmamış olursun.

**En az iki grup gerekir:**

```
grup[0]  kök kemik (tag 0)   parentIdx=255   -> SABIT taban/menteşe
grup[1]  hareketli kemik      parentIdx=0     -> DÖNEN parça (kanat, kapak)
```

Hareket eden parça **çocuk** grupta olmalı. Kök gruba da mutlaka bir
collision ver (yoksa Sollumz o kemiği atlar ve tek gruba düşersin) —
dönme ekseni üzerindeki küçük parçalar bu iş için idealdir, döndüklerinde
konumları zaten değişmez.

Doğrulama: `Groups` listesinde parentIdx=255 olanın boneTag'i **0**
olmalı; hareketli kemiğin tag'i çocuk grupta görünmeli.

### physicsDictionary asla 0 bırakılmaz

Collision `.ydr`/`.yft` içine gömülü olsa bile oyun onu **archetype'ın
physicsDictionary'sinden** bulur. 0 verirsen model görünür ama içinden
geçilir. Vanilla arşivinde tek bir kapı prop'unda bile 0 yoktur
(`v_ilev_gb_teldr` → 2110158618, `prop_ld_garaged_01` → 427433450).

Kendi prop'umuzda doğrusu **kendi ad hash'i**: `-PhysicsDictSelf`.
`textureDictionary` ise dokular gömülüyse 0 kalabilir.

### ytyp tarafı

`assetType` bir **property**dir (alan değil), tipi
`rage__fwArchetypeDef__eAssetType`. Fragment için:

- `assetType = ASSET_TYPE_FRAGMENT` — drawable kalırsa oyun per-bone
  collision kurmaz, tüm emek boşa gider.
- `physicsDictionary = kendi ad hash'i` (0 değil).
- `textureDictionary = 0` — Sollumz dokuları .yft'ye gömer.
- `specialAttribute = 0` — animasyonu script oynatıyorsa bu bir kapı
  sistemi kapısı değildir.

`make_ytyp_override.ps1 -AssetType ASSET_TYPE_FRAGMENT -ClearDicts
-PhysicsDictSelf` bunu üretir.

### Doğrulama

Export "FINISHED" demesi yeterli değil. `cw_to_xml` ile .yft'yi döküp bak:
`<Physics><LOD1>` altında `<Groups>` dolu mu, `<Children>` sayısı bound
sayısına eşit mi, hepsinin `<BoneTag>`'i doğru kemiğin tag'i mi. Çalışan bir
referans fragment varsa aynı alanları yan yana karşılaştır.

## KENDİ SİLAHINI EKLEME (ADD-ON WEAPON)

Kendi 3D silah modelini oyuna sokmak (iskelet eşleme, bileşen/şarjör, meta
üretimi, kaynak yapısı) gerekiyorsa **önce**:

**`references/addon-silah-uretimi.md`** · komut: `/weapon`

Blender açmadan bilinmesi gereken dört şey:

- **Add-on silah vanilla iskeletin üzerine kurulur.** Serbest olan tek şey
  kemiklerin **konumu**; ad ve tag korunur. Referans silahta olmayan
  eklenti yuvası (`WAPScop`, `WAPSupp`...) sonradan eklenemez — şablonu
  buna göre seç. Önce sorgula: `assetdb.py bones <referans_model>`.
- **⛔ `AAPClip` ile `WAPClip` aynı şey değildir.** [ölçüm: 868 model —
  410 ana silah, 458 tek kemikli bileşen] Kural: **modelin kökü `AAP*`,
  silahtaki yuva `WAP*`**. `WAPClip` (tag **1477**) **silahın**
  `.ydr`'sindeki takma noktası; `AAPClip` (tag **0**) **şarjör modelinin**
  kök kemiği — ana silah iskeletinde **hiç geçmez**. Şarjör drawable'ının
  tek vertex group'u `AAPClip` olacak; `WAPClip` yazılırsa şarjör hiç
  bağlanmaz. Aynı kalıp: `AAPSupp`↔`WAPSupp`, `AAPScop`↔`WAPScop`,
  `AAPGrip`↔`WAPGrip`.
- **⚠️ `skeletons.tsv.gz`'de silah satırları 4 kez tekrarlar** (aynı model
  birden fazla RPF/DLC kopyasından indekslendi; `w_ar_assaultrifle` = 64
  satır / **16** kemik). Satır sayarak kemik ya da model sınıflandırma
  yapma — `boneCount` alanını kullan veya `(index, ad, tag)` ile deduplike
  et. Bu atlanırsa 458 bileşen modeli "çok kemikli ana silah" sayılır.
  `assetdb.py bones` **artık deduplike ediyor**, her kemik bir kez basılır;
  dosyayı kendin okuyorsan tuzak yerinde duruyor.
- **Kemik tag'leri sabittir** [ölçüm]: `Gun_Root 0 · Gun_Main_Bone 3360 ·
  Gun_Trigger_Pr 56099 · Gun_Cock1 39439 · Gun_Muzzle 17833 · WAPClip 1477 ·
  WAPSupp 4230 · WAPScop 64805`. Tek istisna kural: **kök kemiğin tag'i
  her zaman 0'dır** (`Gun_GripR` normalde 18308'dir ama kendi modelinin
  kökü olduğunda 0 görünür). Vertex group adları kemik adlarıyla
  **birebir** aynı olmalı, yoksa o parça sessizce hiç sürülmez.
- **⛔ Silahta weight painting YOKTUR, rijit atama vardır.** [ölçüm:
  `w_ar_assaultrifle.ydr` çözüldü] 2556 vertex'in **%100'ü tam 1 kemiğe**
  bağlı, ağırlık toplamı her vertex'te tam **255 (1.0)**, 2+ kemik etkileyen
  vertex **0**, ağırlıksız vertex **0**. Ped'in "4 kemiğe harmanla"
  mantığını silaha taşıma — metal esnemez, parçalar katı döner. Blender'da
  `Assign` **Weight = 1.000** ile yapılır.
- **Kaynak beş `data_file` bildirir** [oyun konsolundan okundu]:
  `WEAPONINFO_FILE`→`meta/weapons.meta`, `WEAPON_METADATA_FILE`→
  `meta/weaponarchetypes.meta`, `WEAPON_ANIMATIONS_FILE`→
  `meta/weaponanimations.meta`, `PED_PERSONALITY_FILE`→
  `meta/pedpersonality.meta`, `WEAPONCOMPONENTSINFO_FILE`→
  `meta/components/<COMPONENT>/weaponcomponents.meta`. **Her bileşen kendi
  klasörünü ve kendi satırını ister**; tek satır bırakmak diğer bileşenleri
  sessizce düşürür.

Meta üretimi **vWeaponsToolkit 1.0.3** ile yapılır (sonraki build'ler bozuk).
Test: `restart <kaynak>` + `str_requestFlush` (istemci konsolu, canary build)
— **silahı önce elden bırak**; tutmazsa sunucudan çıkıp yeniden bağlan.

İki nokta daha, ikisi de sessiz arıza kaynağı:

- **⛔ `weaponcomponents.meta` → `<AttachBone>` alanına `AAP*` yazılır,
  `WAP*` değil.** [ölçüm: 4 vanilla dosyada 318 girdi — 318'i `AAP*`,
  sıfırı `WAP*`] Alan silahtaki yuvayı değil, **bileşen modelinin kendi
  kök kemiğini** gösterir. İskelet tarafındaki `WAP*`/`AAP*` ayrımıyla

- **⛔ Base **ve** `_hi` modelin ikisi de gerekir.** Kemik taşındığında

**sessizce** kırar: extent'e dokunmak (haritanın tamamında collision gitti),
LOD zincirinin tamamı + `hei_` ikizleri, dokuların modelde **olmaması**
(yedi vanilla modelin hiçbirinde gömülü doku yok), aynı doku adının farklı
sözlükte farklı içerik taşıması (175 kopyadan 22'si).

**`references/vanilla-parca-degistirme.md`**
Doku sözlüğü indeksi: `scripts/ytd_index.ps1` · `scripts/ytd_ara.ps1`

## GÖRSEL GEREKTİĞİNDE — üretme, öner ve prompt ver

Ekran arka planı, ikon, logo, doku, UI görseli gerektiğinde **rastgele bir
şey üretme ya da yer tutucu uydurma.** Sırayla:

1. Fikri anlat: ne göstereceği, hangi objede duracağı, hangi mesafeden
   okunacağı, ton/renk.
2. Kullanıcıya **hazır bir prompt** ver ve fotoğrafı **kullanıcının**
   üretmesini iste. Prompt en-boy oranını (panelin `resW:resH` oranıyla aynı),
   çözünürlüğü ve arka plan davranışını içersin.
3. Görsel gelene kadar düzeni CSS ile kur, doğru ölçüde boş kutu bırak —
   görsel gelince tek dosya değişir.

## NE ZAMAN YETMEZ

- **Fragment iç yapısı / bone listesi** → .yft incelenmeli.
- **Animasyonun süresi / eventleri** → .ycd incelenmeli.
- **Custom (sunucu) MLO'larının iç yerleşimi** → indeks vanilla MLO'ları
  genişletir; sunucunun kendi MLO'ları için `/asset-build` ile `-ExtraFolders`
  vermek archetype'ları getirir ama iç entity genişletmesi vanilla ymap'lere
  bağlıdır.

Bu durumlarda tahmin yürütme; kullanıcıya CodeWalker'da neye bakması
gerektiğini söyle veya oyun içi ölçüm iste.
